# Honey Flowers — программа лояльности «Медовые соты»

Программа лояльности для цветочного магазина Honey Flowers (Ташкент), работает как Telegram Mini App внутри бота магазина.
Две механики: **соты**: карта из 10 покупок, в некоторых ячейках спрятаны подарки; **мёд**: кешбэк баллами (1 мёд = 1 сум), процент зависит от уровня клиента (1% → 3% → 5%).
Флорист находит клиента по телефону или QR и вводит сумму покупки. Сервер начисляет мёд, двигает пчёлку по сотам и выдаёт подарки, а бот присылает клиенту уведомление.

> Статус: **тестовая версия на Cloudflare**. Один Worker отдаёт Mini App, JSON API и вебхук бота и каждый час запускает «ночную» задачу (сгорание мёда и напоминания). База данных — Cloudflare D1.
> Все числа в правилах пока заглушки: их заменят ответы клиента на анкету (таблица ниже). Владелец может менять их в приложении, каждое изменение создаёт новую версию правил.
>
> **Как выложить:** [docs/DEPLOY.md](docs/DEPLOY.md) — пошаговая инструкция «по кнопкам».

## Архитектура

```
Telegram ──► бот (вебхук) ─┐
Mini App ──► /api/*  ──────┼──► apps/worker (Hono на Cloudflare Workers)
cron каждый час ───────────┘        │  LoyaltyService (packages/service): загрузить → движок → сохранить → уведомить
                                    │  движок правил (packages/core): чистые функции, без IO и без часов
                                    ▼
                              Cloudflare D1 (SQLite)      статика Mini App (apps/miniapp/dist)
```

- **Один Worker, один адрес.** Запросы на `/api/*`, `/telegram/*`, `/setup` и `/health` обрабатывает код Worker'а. Все остальные пути отдают статику Mini App с SPA-fallback на `index.html`.
- **Контракт фронтенда и бэкенда** описан в `packages/contracts` (`@honey/contracts`, только типы). Mini App и Worker импортируют одни и те же типы.
- **Конкурентность без блокировок.** В D1 нет `SELECT … FOR UPDATE`. Поэтому каждая команда сохраняется одним `db.batch([...])` (это транзакция), и первым запросом пакет вставляет `(client_id, загруженная_версия + 1)` в `client_versions`. Если параллельный запрос уже записал эту версию, срабатывает первичный ключ, весь пакет откатывается, и сервис повторяет команду на свежих данных, не больше 3 раз. Списать один и тот же мёд дважды так нельзя (есть тест).
- **Уведомления.** Сообщения в бот уходят после записи в базу, в фоне (`ctx.waitUntil`). Ошибка Telegram не ломает покупку и записывается в `notifications_log`.
- **Часы.** Везде используется `now = реальное время + settings.clock_offset_days`. В тестовом режиме время можно «перемотать» (`/api/test/clock`).

## Как запустить

Нужен Node.js 22+.

```bash
npm ci
npm test            # все тесты: core, service, api, worker (worker — в рантайме workerd с локальной D1)
npm run build       # пакеты + Mini App (если есть) + проверка типов Worker'а
npm run dev         # wrangler dev --local на http://127.0.0.1:8787 (сначала применяет миграции к локальной D1)
npm run deploy      # wrangler deploy (нужен `npx wrangler login`); обычно деплой идёт через Workers Builds
npm run e2e -w apps/miniapp   # сквозной тест Mini App (jsdom) против запущенного `npm run dev` на :8787
npm run qa          # QA-набор (qa/): сценарии, инварианты, фазз, конкурентность, модельный тест, нагрузка; свой Worker на :8797 и чистая D1
```

Для `npm run dev` скопируйте `apps/worker/.dev.vars.example` в `apps/worker/.dev.vars`. Без бота можно проверять всё через заголовки `X-Test-User` + `X-Test-Key` (примеры curl есть в [docs/DEPLOY.md](docs/DEPLOY.md#локальный-запуск-для-разработчика)).
Если `apps/miniapp/dist` ещё нет, `apps/worker/scripts/ensure-assets.mjs` создаст страницу-заглушку, и wrangler не упадёт.

### Авторизация и роли

Mini App передаёт в каждом запросе `Authorization: tma <Telegram.WebApp.initData>`. Подпись проверяется по `BOT_TOKEN` по алгоритму из документации Telegram, `auth_date` должен быть не старше 24 часов.
В тестовом режиме (`TEST_MODE = "1"`) вместо этого можно передать `X-Test-User: <id ≥ 900000000>` вместе с `X-Test-Key: <секрет TEST_KEY>` и, необязательно, `X-Test-Name`. Настоящие Telegram ID через заголовок не принимаются (их выдаёт только подпись initData), без `TEST_KEY` тестовый вход выключен. Просроченная подпись (старше 24 часов) отвечает `401 { code: "expired" }` — приложение просит открыть себя заново.

Тестовые функции (`/api/test/*`, смена роли, часы, демо, вход `X-Test-User`) в тестовом режиме доступны только тестировщикам из `TEST_USERS` (Telegram ID и/или телефоны `+998…`, `apps/worker/src/lib/testAccess.ts`); пустой `TEST_USERS` = все на полигоне и **никто** на Worker'е заказчика. Остальные пользователи видят рабочий режим (`MeDTO.testMode = false`, без «🧪 Тест»). Подробно — [docs/DEPLOY.md](docs/DEPLOY.md#тестовый-режим-test_mode--1-и-список-тестировщиков-test_users).

Роль: у тестировщика сначала смотрим выбранную через `/api/test/role`, иначе активную запись в `staff`, иначе `client`. У всех остальных (и вне тестового режима) учитывается только таблица `staff`.
Сотрудников добавляет владелец (`POST /api/owner/staff`). Первого владельца можно назначить ссылкой `/setup?key=…&owner=<+998телефон или id:TelegramID>`. Последнего активного владельца нельзя понизить или отключить.

### Бот

`/start` — приветствие (ru + строка на uz), кнопка «📱 Поделиться номером» и меню: «🐝 Открыть медовую карту», «🍯 Как копить мёд», «🌐 Язык», а владельцу ещё «📊 Сводка за сегодня».
Контакт принимается, только если пользователь отправил **свой** номер. Бот приводит его к виду `+998…`, создаёт клиента с кодом `HF` + 4–6 цифр и начисляет приветственный бонус через движок.
`/card` — кнопка карты. `/help` — как работает программа (по действующим правилам). `/stats` — только владельцу: покупки, выручка, новые клиенты, начисленный и списанный мёд за сегодня и за неделю (из `stats_daily`). `/lang` — выбор языка. Все тексты на ru и uz лежат в `apps/worker/src/bot/texts.ts`.
Бот присылает уведомления о начислении, открытом подарке, новом уровне, скором сгорании, сгорании и отмене покупки.

## База клиентов владельца: сводная таблица `client_stats`

**Зачем.** Баланс, уровень, срок сгорания и подарки клиента выводятся из его журнала (`points_ledger`, `purchases`, `rewards`). Для одной карточки это дёшево, но список из 10 000+ клиентов с фильтрами и сортировкой пришлось бы считать по всем строкам журнала на каждый запрос. На бесплатном плане Cloudflare (10 мс CPU, 50 запросов к D1 за вызов, 5 млн прочитанных строк в сутки) так нельзя. Поэтому у каждого клиента есть одна строка `client_stats` (миграция `0004_client_stats.sql`): баланс, сумма для уровня, число покупок, последняя покупка, уровень, доступные подарки, «якорь» сгорания и последний день действия мёда.

**Как она остаётся верной.**
- Все записи движка идут через `saveOutcome`, это один `db.batch` (транзакция). `LoyaltyService` передаёт туда состояние **после** команды, и сводка считается теми же функциями движка, что и карточка клиента (`lib/clientStats.ts`). Её upsert — ещё одна инструкция того же пакета. Если параллельная запись выиграла гонку версий, откатывается весь пакет вместе со сводкой.
- `createClient` вставляет пустую строку сводки вместе с клиентом, удаление клиента убирает её. Ночная задача передаёт состояние после сгорания.
- Новая версия правил пересчитывает в SQL уровень (по сумме и понижению) и срок сгорания (по якорю) у тех строк, где они изменились.
- Открытие карточки (`GET /api/owner/clients/:id`) пересчитывает производные поля сводки (уровень, «действует до») и чинит их, если они разошлись (обычно ничего не пишет; запись идёт, только если версия клиента не изменилась). Итоги (баланс, число покупок, суммы для уровня) пишутся только в пакете вместе с фактами и проверяются QA-инвариантами.
- Без записи сводка не узнает две вещи: что окно уровня (`levels.windowMonths`) сдвинулось и что просроченный мёд ещё не сжёг ночной ход. Обе вещи исправит следующая запись по клиенту или ночная задача, а карточка всегда показывает живое значение. Миграция заполняет сводку для уже существующих клиентов.

**Сколько стоит.** Страница списка — это один запрос: SQLite идёт по индексу колонки сортировки (`client_stats(last_purchase_at|spent|balance, client_id)`, `clients(name, id)`, `clients(created_at, id)`) и останавливается после 31 подходящей строки. Пагинация по курсору (значение сортировки + id): если между загрузками страниц кто-то купил, ни один клиент не повторится и не пропадёт — **кроме самого покупателя**, если покупка подняла его выше курсора (например, в сортировке «последняя покупка» или «больше всех потратили»): в этом проходе списка он уже не покажется, он виден при следующем открытии списка сверху. Это свойство keyset-пагинации; снимок списка на момент первой страницы потребовал бы хранить его на сервере. Тест `apps/worker/test/ownerClients.test.ts` проверяет: при 1 000 клиентов страница из 30 читает ≤ 200 строк и делает ≤ 6 обращений к D1. Поиск по точному коду идёт по уникальному индексу. Поиск по части имени или телефона и фильтр, который противоречит сортировке (например, низший уровень при сортировке «больше всех потратили»), просматривают больше строк, но это всё равно один запрос.

## Статистика: дневные агрегаты `stats_daily`

**Зачем.** Статистика владельца (`/api/owner/stats`) читала ~90 тыс. строк за один просмотр при 2 000 клиентов (бесплатный D1 — 5 млн строк в сутки, т. е. ~55 просмотров), обзор кабинета — ~40 тыс. Теперь у каждого календарного дня (Ташкент) есть одна строка `stats_daily` (миграция `0007_stats_daily.sql`) плюс строка `'*'` «за всё время»: покупки и выручка, «первые» покупки (повторные = покупки − первые), покупатели дня, клиенты, чья последняя / предпоследняя покупка в этот день, новые и импортированные клиенты, мёд начислен / списан / сгорел / стартовый из импорта, подарки открыты / выданы, отмены.

**Как остаётся верной.** Каждая запись меняет агрегаты в том же `db.batch`, что и факты (`saveOutcome`, `createClient`): строки журнала мёда только добавляются — их вклад считается в Worker'е; у покупки и подарка статус может меняться — пакет вычитает вклад строки до записи и прибавляет после (SQL читает одну строку), поэтому отмена, выдача и аннулирование подарка точны при любом прошлом статусе. Импорт и его отмена, демо-данные и их удаление, «сбросить мои данные» прибавляют/вычитают вклад набора клиентов одним SQL (`lib/statsDaily.ts`). Миграция заполняет таблицу из существующих данных. QA-проверка (`qa/lib/invariants.mjs`) пересчитывает таблицу из сырых строк и сравнивает.

**Что считается.** Демо-клиенты — как настоящие. Клиенты из импорта не «новые», их стартовый мёд не «начислен» (в «мёд на счетах» входит). «Активные клиенты» за период ровно = различные покупатели: для периода, который заканчивается сегодня, — сумма «последних покупателей» по дням; для прошедших окон (прошлый период, недели/месяцы на графике) — один раз `COUNT(DISTINCT)` по индексу и кеш `stats_buyers` (сбрасывается при отмене покупки в этом окне, демо-данных, перемотке часов). «7 дней» и «90 дней» в мини-приложении — календарные дни по Ташкенту, включая сегодня. Бот `/stats` считает мёд так же, как статистика владельца (отмены уменьшают начисленное, стартовый мёд импорта не входит).

**Сколько стоит.** `/api/owner/stats` и `/stats` — один запрос, ≤ ~100 строк. Обзор кабинета — 2 обращения к D1, ~2 × (дней периода) строк (90 дней ≈ 250 строк при повторном просмотре; первый просмотр нового прошедшего окна один раз считает его покупателей по индексу).

**Экспорт CSV.** Файл в UTF-8 с BOM (иначе Excel покажет кракозябры вместо кириллицы), разделитель `;` (так ждёт Excel в русской и узбекской локали), даты `ГГГГ-ММ-ДД ЧЧ:ММ` по Ташкенту, ответ отдаётся потоком с `Content-Disposition: attachment`. База клиентов читается из сводки кусками по 500 строк. Операции читаются кусками по 500 строк по индексам времени, за период по умолчанию 90 дней. Больше 50 000 строк — ошибка 400 с просьбой выбрать период короче. Ссылки из `POST /api/owner/export/link` хранятся в `export_links`, срабатывают один раз (атомарный `UPDATE … RETURNING`) и живут 10 минут.

## Как устроен конфиг правил

- Все настраиваемые числа и флаги лежат в одном объекте `LoyaltyRules` (`packages/core/src/rules.ts`). Его проверяет zod-схема: пороги уровней должны идти по возрастанию, подарки — стоять внутри карты, часовой пояс — существовать.
- Значения по умолчанию — `packages/core/src/defaultRules.ts`. Возле каждого поля в комментарии указан номер вопроса анкеты, ответ на который его определяет.
- Правила **версионируются**: поле `version` и таблица `rules_versions` (JSON правил). Текущую версию указывает `settings.rules_version`. Каждая покупка сохраняет `rules_version_id`, поэтому при смене процентов старые покупки не пересчитываются. Версию 1 (`defaultRules`) Worker записывает в базу при первом обращении.
- Владелец редактирует часть правил через `GET/PUT /api/owner/rules` (`EditableRulesDTO`): уровни, минимум для соты, лимит сот в день, лимит оплаты мёдом, срок сгорания и напоминания, приветственный бонус, подарки в сотах. Коды подарков: `card`, `delivery`, `discN` (скидка N%), `mini`.
- Движок чистый: команда получает `(rules, state, input, now)` и возвращает `Outcome` — новые записи журнала мёда, ходы по сотам, открытые подарки, смену уровня, события для уведомлений и `warnings`. Сохранение и отправку делает API.
- Баланс по определению равен сумме журнала `points_ledger` (журнал только дополняется, в БД это обеспечивает триггер). Чтобы не читать весь журнал, его итог хранится в `client_stats.balance` и обновляется в том же пакете, что и каждая запись.

### Клиенты с длинной историей (ограниченная загрузка состояния)

Раньше любая команда и экран клиента загружали и «проигрывали» всю его историю: клиент с ~1 000 покупок стоил ~3 800 прочитанных строк и 140–250 мс на `/api/me`, покупке и карточке. Теперь (`apps/worker/src/db/stateLoader.ts`, миграция `0010_bounded_state.sql`) загружается только то, на что смотрит движок: несколько последних покупок, две последние действующие (якорь сгорания), хвост ходов по сотам (откат при отмене), последние подарки и доступные подарки (все — если правило сгорания сбрасывает карту), последнее сгорание и последнее начисление, приветственный бонус, ключи напоминаний, а также строки, которые команда называет явно (покупка для отмены, ключи идемпотентности, подарок). Остальное движок получает как итоги (`ClientState.folded`): `client_stats.balance`, `purchases_count`, `level_sum` / `level_count` (сумма и число покупок для уровня после «понижения»), `gifts_available` минус загруженное. Итоги пишутся в том же пакете, что и факты, поэтому точны. С окном уровня (`levels.windowMonths`) загружаются все покупки внутри окна. История в карточке — отдельный SQL с курсором (`lib/history.ts`), 50 строк на страницу; в карточке владельца — кнопка «Показать ещё». Ночная задача грузит ограниченные состояния сразу для 100 клиентов теми же ~10 запросами.

Доказательства: `packages/core/test/folded.test.ts` — на случайных историях (4 набора правил, по 40 историй × 60 команд) все команды и производные значения на урезанном состоянии совпадают с полным; `apps/worker/test/heavyClient.test.ts` — клиент с 1 000 покупок читает столько же строк, сколько клиент со 100 (`/api/me` ≈ 400, карточка ≈ 400, покупка ≈ 470, отмена ≈ 490; клиент с 10 покупками — 160–260), а значения совпадают с расчётом по полной истории.
- Все «дни» (лимит сот в день, сгорание через 90 дней, окно уровня) считаются по календарю **Asia/Tashkent**, а не по UTC. Cron `0 * * * *` запускается каждый час; сообщения клиентам он отправляет только с 09:00 до 21:00 по Ташкенту (см. ниже).
- Ежедневная задача не перебирает всех клиентов: у каждого клиента хранится дата следующей проверки (`clients.next_check_on`, миграции 0003 и 0008) — ближайшее неотправленное напоминание или день сгорания, `NULL` — ничего не ожидается (например, нулевой баланс). Дата **точно** вычисляется при каждой записи в том же пакете (`saveOutcome`, регистрация, импорт, демо-данные; `lib/expirySchedule.ts`), а смена правил и перемотка тестовых часов пересчитывают её у всех одним SQL (по 5 000 клиентов на инструкцию). Задача читает только `next_check_on <= сегодня`, самые ранние даты первыми (индекс), поэтому день с сотнями покупок больше не отодвигает напоминания и сгорания.
- **Лимиты бесплатного плана (`src/cron.ts`).** Задача запускается **каждый час** и укладывается в ≤ 45 подзапросов (обращения к D1 + запросы к Telegram; лимит Workers Free — 50): правила, список клиентов на сегодня (до `CRON_MAX_CLIENTS` = 100), их состояния — один пакет, **все** записи запуска (сгорание, ключи напоминаний, сводки, `stats_daily`, `next_check_on`, очередь сообщений) — один `db.batch`, затем до `CRON_MAX_SENDS` = 25 сообщений, отметка об отправке и строка `cron_runs` (там же `subrequests`, `sent`, `queued`). 2 000 клиентов, у которых всё случилось в один день, обрабатываются за 20 часовых запусков. Сгорание и напоминания применяются в любой час, а сообщения о них попадают в очередь `outbox` (миграция 0009) **в том же пакете**, что и факты, и отправляются с 09:00 до 21:00 по Ташкенту. Строка очереди помечается отправленной только после ответа Telegram «ok»; временная ошибка — повтор в следующих запусках (через 10 мин, 20 мин … до 6 ч, до 8 попыток), постоянная (бот заблокирован) — статус `failed`; всё пишется в `notifications_log`. Напоминание, которое ждало в очереди, при отправке пересчитывает «осталось N дней», а если срок уже прошёл — не отправляется (о сгорании придёт своё сообщение). Если общий пакет не прошёл (в ту же секунду кто-то купил), клиенты записываются по одному, пока хватает лимита; не записанный клиент остаётся «на сегодня» и обрабатывается следующим запуском. Telegram-сообщения — по одному подзапросу, поэтому их не больше ~25 в час ≈ 300 в день: массовое сгорание у 2 000 клиентов рассылается за несколько дней (очередь видна в `/health` → `lastCron.queued`).

## Принятые решения по правилам (проверить с клиентом)

- Уровень считается по **полной** сумме покупки, а кешбэк — только по **оплаченной деньгами** части (сумма − мёд − скидка).
- Процент берётся по уровню **до** покупки. Если покупка переводит клиента на новый уровень, он действует со следующей покупки (событие `level_up`).
- Если в заказе есть категории без кешбэка, списанный мёд и скидка 10% распределяются по строкам пропорционально. Подарок «бесплатная доставка» или «открытка» уменьшает только свою строку.
- Лимит списания считается от полной суммы заказа и не может быть больше остатка после скидки.
- Мёд сгорает в календарный день «последняя покупка + 90». В день 89 он ещё есть. Таймер стартует с регистрации (с момента начисления приветственного бонуса), так что приветственный бонус тоже сгорает. Списание мёда без покупки срок **не** продлевает. Мёд, вернувшийся после отмены покупки, подчиняется тому же сроку.
- `balance_and_level_down`: клиент опускается на один уровень, и старые покупки больше не идут в счёт следующего уровня. `reset_all` дополнительно начинает новую карту сот и аннулирует неиспользованные подарки.
- **Отмена покупки** («Отменить» у флориста) — исключительный инструмент сотрудника для исправления ошибки на кассе (решение владельца). Клиент отменить не может. Отмена разрешена только в течение `reversalWindowHours` часов после покупки (правило с версиями, по умолчанию 24, владелец меняет его на экране «Правила», 1–720 ч) и отклоняется с ошибкой 409, если:
  - прошло больше времени — «Отмена возможна только в течение N ч после покупки…»;
  - открытый этой покупкой подарок уже выдан — «Подарок за эту покупку уже использован — отменить нельзя…» (подарок за одну и ту же соту не может быть получен дважды);
  - мёд с этой покупки уже потрачен, т. е. после отмены баланс ушёл бы в минус — «Мёд с этой покупки уже потрачен — отменить нельзя. Если нужно исправить баланс, это может сделать владелец через «Скорректировать мёд».».
  Поэтому отмена никогда не оставляет отрицательный баланс и не даёт второй подарок за ту же соту. В списке операций флориста у таких покупок вместо кнопки «Отменить» показана причина (`OperationDTO.reversible` / `reverseBlocked`), сервер всё равно проверяет заново. Исправить баланс в остальных случаях может владелец ручной корректировкой (как раньше). Отмена покупки с оплатой мёдом в том же окне разрешена: мёд возвращается. Отмена возвращает списанный мёд и использованный в ней подарок (но не возвращает подарок, если открывшая его покупка уже отменена или карта с тех пор сброшена). Пчёлка откатывается, только если это был последний ход по сотам, иначе приходит предупреждение; вместе с последним ходом откатываются и «застрявшие» ходы ранее отменённых покупок. Отменённая покупка не занимает дневной лимит сот. Открытый этой покупкой и ещё не использованный подарок аннулируется (`revoked`), пчёлка возвращается на соту назад. Начисленный мёд снимается, только если он ещё не сгорел.
- Повтор с тем же `idempotencyKey` возвращает исходный результат. Тот же ключ с другой суммой даёт ошибку 409.

## Что ещё не сделано

- **Фронтенд Mini App** (`apps/miniapp`) делается параллельно по контракту `@honey/contracts`.
- **Категории покупки.** API принимает одну сумму и считает её «цветами». Строки по категориям (доставка, открытки) движок поддерживает, но в контракт они пока не выведены.
- **Перенос старой базы**: ручная корректировка есть (`POST /api/owner/clients/:id/adjust`), массового импорта нет.
- **День рождения клиента**: фильтр «ДР на неделе» читает `clients.birthday`, но спросить дату у клиента пока негде.
- **Подарок на день рождения и «важные даты»**: таблица есть, логики нет.
- **Рассылки владельца**: нет.
- **Postgres** (`db/migrations/001_init.sql`, `docker-compose.yml`) оставлен на случай переезда с D1, сейчас не используется.

## Кабинет владельца на компьютере

Глубокая аналитика вынесена из мини-приложения на отдельную страницу `console.html` (тот же Worker, тот же дизайн — темы из `apps/miniapp/src/config/themes.ts`). В мини-приложении остаются только главные цифры.

### Как открыть

1. В медовой карте (роль «Владелец») → **Статистика** → **«Открыть кабинет на компьютере»**.
2. Бот присылает в чат ссылку `https://…/console.html#t=…` — откройте её на компьютере (в Telegram Desktop достаточно нажать). Ссылку можно и скопировать из приложения.
3. Ссылка одноразовая и живёт **10 минут**; в базе хранится только её SHA-256. После входа браузер получает сессию на **12 часов** (`Authorization: Bearer`, подпись HMAC-SHA256 ключом `WEB_SESSION_SECRET`, а если он не задан — ключом, выведенным из `BOT_TOKEN`).
4. **«Выйти»** завершает все сессии этого владельца на всех компьютерах. Если владельца разжаловали, кабинет сразу отвечает 403. Просроченная или уже использованная ссылка показывает экран «Ссылка устарела, запросите новую в приложении».
5. Сессия кабинета пускает только в `/api/owner/*` и `/api/web/*` — ни кассы, ни клиентского API.
6. Тестовая версия (`TEST_MODE=1`): кабинет открывается и без бота — тем же тестовым входом, что и мини-приложение в браузере (имя + `TEST_KEY`, нужна роль «Владелец»).

Необязательный секрет: `WEB_SESSION_SECRET` (`npx wrangler secret put WEB_SESSION_SECRET`). Его смена разлогинивает все браузеры.

### Разделы

| Раздел | Что показывает |
|---|---|
| Обзор | За выбранный период и в сравнении с предыдущим таким же: выручка через программу, покупки, средний чек, активные и новые клиенты, доля повторных покупок, мёд начислен / списан / сгорел, подарки открыты / выданы; график по дням, неделям или месяцам (выбирается сам по длине периода). |
| Клиенты | Таблица с фильтрами: период, уровень, число покупок, сумма, средний чек, последняя покупка (активные < 30 дн., засыпающие 30–60, ушедшие 60+, ещё не покупали), месяц дня рождения, дата регистрации, есть неиспользованный подарок, «из импорта, ещё не в Telegram». Сортировка по столбцам, постраничная подгрузка, число найденных и их сумма, выгрузка ровно этого списка в CSV. |
| Покупки | Операции за период: покупки, отмены, списания, корректировки, выдача подарков, приветственные бонусы, сгорания. Фильтры: тип, сотрудник, сумма заказа. Строка итогов и CSV. |
| Удержание | По месяцу первой покупки: доля клиентов, вернувшихся за второй покупкой (в другой день) за 30 / 60 / 90 дней. |
| Импорт базы | Перенос старой базы клиентов (см. ниже) и список прошлых импортов с отменой. |

Все фильтры лежат в адресной строке (`console.html?s=clients&from=…&minCount=3…`): вид можно добавить в закладки или переслать (откроется у того, кто уже вошёл). CSV — UTF-8 с BOM, разделитель `;`, даты по Ташкенту, не больше 50 000 строк; файл собирается в браузере по страницам по 1 000 строк.

**Скорость и лимиты Cloudflare Free.** Каждый экран — 3–4 обращения к D1 (часы, проверка сессии, правила, один пакет данных), все агрегаты считаются в SQLite, списки — с `LIMIT` и курсором. Раздел «Клиенты» читает сводку `client_stats` (баланс, число покупок, последняя покупка, уровень, подарки); сами покупки читаются, только если выбран период или нужна сортировка/фильтр по сумме или среднему чеку. Тест `apps/worker/test/console.scale.test.ts` (2 000 клиентов, 20 000 покупок) проверяет число запросов и точность итогов. Порядок «прочитанных строк» на такой базе: обзор за 90 дней ≈ 250 (из `stats_daily`, см. выше; раньше ≈ 40 тыс.), клиенты за всё время ≈ 12 тыс., клиенты за полгода с суммами ≈ 22 тыс., журнал за месяц ≈ 5–10 тыс., удержание ≈ 28 тыс. При дневном лимите 5 млн это сотни просмотров в день.


### Импорт базы клиентов

1. Раздел **«Импорт базы»** → выбрать файл **.xlsx** или **.csv** (UTF-8 или Windows-1251; разделитель `;`, `,` или табуляция; старый `.xls` — пересохранить в `.xlsx`). Файл читается в браузере.
2. Колонки определяются по заголовкам (рус./англ./узб.: телефон / phone, имя / ФИО / name, день рождения / birthday, баланс / бонусы / баллы, сумма покупок, кол-во покупок, последняя покупка); строку заголовков и любую колонку можно поправить вручную.
3. Телефоны приводятся к `+998XXXXXXXXX` (подходят `901234567`, `998901234567`, `+998 (90) 123-45-67`, `8 90 …`, числа из Excel). Строки без телефона, с не узбекским номером и повторы номера в файле пропускаются; нераспознанная дата или сумма — замечание, поле просто не переносится.
4. **«Проверить по базе»** (пробный прогон, ничего не пишет) показывает по каждой строке: новый клиент / уже в базе / ошибка, и сколько мёда будет начислено.
5. **«Импортировать»** — частями по 100 строк. Если связь оборвалась, «Продолжить загрузку» дошлёт остаток: повтор части ничего не задваивает.

Флажки (правила ещё не решены, поэтому выбор за владельцем):

- **Начислить стартовый мёд из колонки баланса** — запись `manual_adjust` «Импорт базы: стартовый баланс» с ключом `import:<импорт>:<телефон>`; мёд сгорает по общим правилам (90 дней без покупок, отсчёт с даты импорта).
- **Учитывать прошлую сумму покупок для уровня** — клиент получает уровень, достигнутый прошлой суммой (или числом покупок, если уровни считаются по количеству), как «нижнюю планку» (`level_override`).
- **Засчитать прошлые покупки в соты** (по умолчанию выключено) — пчёлка встаёт на соту по числу прошлых покупок, не дальше предпоследней; подарки за пройденные соты не выдаются.

Как это работает с регистрацией: у импортированного клиента есть телефон, но нет Telegram (в `clients.telegram_id` — отрицательная заглушка −998XXXXXXXXX, бот такому клиенту не пишет; клиент сразу появляется в списке «Клиенты» с мёдом и уровнем — строка `client_stats` пишется вместе с импортом). Когда человек сам делится этим номером в боте (или в мини-приложении), он **забирает** эту карту: тот же код, баланс, уровень и история, без дубликата и без ошибки «номер уже привязан» (`registerWithPhone` → `claimClient`). Забрать можно только клиента с записью в `client_imports` и `demo = 0`: демо-клиенты тестовой версии (у них тоже отрицательные id, но из другого диапазона −990 000 000…) никогда не отдаются реальному человеку. Если у этого Telegram-аккаунта уже есть своя карта, автоматического слияния нет — бот, как и раньше, просит обратиться к флористу.

Повторный импорт того же номера (в любом следующем файле) только дополняет имя и день рождения (у клиентов, уже вошедших в Telegram, — только пустые поля) и **никогда** не начисляет мёд второй раз. Номер, занятый демо-клиентом (тестовая версия), не трогается: строка пропускается с пояснением — после «Удалить демо-данные» импорт можно повторить. Импорт можно **отменить**, пока ни один из созданных им клиентов не вошёл в Telegram, ничего не купил и у него не было других движений мёда (включая сгорание): созданные клиенты удаляются вместе со стартовым мёдом и сводкой, а у уже существовавших клиентов возвращаются прежние имя и день рождения (если их с тех пор не меняли). В списке импортов остаётся запись «отменён».

В мини-приложении (Статистика) клиенты из импорта не считаются «новыми», а их стартовый мёд — «начисленным» (в «мёд на счетах» он входит); демо-клиенты считаются как настоящие.

### Открытые вопросы владельцу по импорту

1. Переносить ли **баланс бонусов** из старой базы и 1 к 1 ли (1 старый бонус = 1 мёд = 1 сум)? Нужен ли потолок стартового мёда?
2. С какой даты считать **сгорание** перенесённого мёда: с даты импорта (сейчас), с даты последней покупки в старой базе или дать отдельный срок (например, 30 дней на первый визит)?
3. Давать ли **уровень** по прошлой сумме покупок сразу, и за какой период считать прошлые покупки (всё время или последние N месяцев)? Сейчас это «нижняя планка» уровня, а сумма до следующего уровня копится заново.
4. Засчитывать ли **прошлые покупки в соты** и выдавать ли тогда подарки за пройденные соты?
5. Начислять ли **приветственный бонус** клиенту из старой базы, когда он впервые заходит в Telegram (сейчас — да, если бонус включён в правилах)?
6. Что делать, если человек из старой базы **уже успел** зарегистрироваться в боте с другим номером: объединять карты вручную, по заявке?
7. Можно ли писать импортированным клиентам **первыми** (SMS-приглашение в бота) — есть ли согласие на рассылку в старой базе?
8. Чьё **имя** главнее: из базы магазина или из Telegram (сейчас у вошедших в Telegram имя не перезаписывается)?
