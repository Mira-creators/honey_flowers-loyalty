# Как выложить тестовую версию на Cloudflare

Инструкция для человека без опыта с серверами. Займёт 20–30 минут.
В итоге получится ссылка вида `https://honey-loyalty.<ваше-имя>.workers.dev`, а в Telegram-боте появится кнопка «Медовая карта».

Один Cloudflare Worker делает всё сразу:

- показывает Mini App (страницы приложения);
- отвечает на запросы приложения (`/api/...`);
- принимает сообщения бота (`/telegram/webhook`);
- каждый час сжигает просроченный мёд и готовит напоминания; сообщения клиентам отправляет с 09:00 до 21:00 по Ташкенту.

Данные хранятся в базе **Cloudflare D1**. Это бесплатно в пределах лимитов Cloudflare, для теста их хватает с большим запасом.

---

## Что понадобится

1. Аккаунт на [GitHub](https://github.com), в нём репозиторий с этим проектом.
2. Аккаунт на [Cloudflare](https://dash.cloudflare.com/sign-up). Подходит бесплатный, банковская карта не нужна.
3. Telegram-бот и его токен. Чтобы получить токен, напишите [@BotFather](https://t.me/BotFather) команду `/newbot` (или `/token` для существующего бота). Токен выглядит так: `7000000001:AAH...`.
4. Три случайных пароля: для вебхука, для ссылки настройки и для тестового входа из браузера. Их можно сгенерировать на [1password.com/password-generator](https://1password.com/password-generator). Используйте только латинские буквы и цифры, длиной 30–40 символов. Сохраните все три в заметках:
   - `WEBHOOK_SECRET`: например `k3J9xQ...`
   - `SETUP_KEY`: например `Zp81Lm...`
   - `TEST_KEY`: например `Qw7tRe...` — его вы будете давать тестировщикам, которые открывают приложение в обычном браузере (без него тестовый вход не работает)

## Шаг 1. Создать базу данных D1

1. Откройте [dash.cloudflare.com](https://dash.cloudflare.com) и войдите.
2. В меню слева выберите **Storage & Databases → D1 SQL Database**.
3. Нажмите **Create Database** (или **Create**).
4. В поле **Name** впишите ровно `honey-loyalty`. Location можно оставить автоматическим. Нажмите **Create**.
5. Откроется страница базы. Скопируйте **Database ID**: это длинная строка вида `a1b2c3d4-....`

Таблицы создавать вручную не нужно: их создаст деплой (шаг 3).

## Шаг 2. Вписать ID базы в проект

1. Откройте репозиторий на GitHub и перейдите в файл `apps/worker/wrangler.toml`.
2. Нажмите карандаш ✏️ (**Edit this file**).
3. Найдите строку

   ```toml
   database_id = "00000000-0000-0000-0000-000000000000"
   ```

   и замените нули на скопированный Database ID. Кавычки оставьте.
4. Нажмите **Commit changes…** → **Commit changes**.

> Тестовый режим (`TEST_MODE`) и список тестировщиков (`TEST_USERS`) задаются переменными сборки — см. раздел «Тестовый режим» в конце документа.

## Шаг 3. Подключить GitHub к Cloudflare (автоматический деплой)

1. В Cloudflare откройте **Workers & Pages** → **Create** (**Create application**).
2. Выберите **Import a repository** (или вкладку **Workers → Connect to Git**).
3. Нажмите **Connect GitHub**, разрешите доступ к нужному репозиторию и выберите его.
4. Заполните настройки:

   | Поле | Что вписать |
   |---|---|
   | **Project name** / Worker name | `honey-loyalty` (имя должно совпадать с `name` в `wrangler.toml`) |
   | **Production branch** | `main` |
   | **Root directory** (Path) | `apps/worker` |
   | **Build command** | `cd ../.. && npm ci && npm run build` |
   | **Deploy command** | `npx wrangler d1 migrations apply honey-loyalty --remote && npx wrangler deploy` |

   Если в разделе **Build variables** (переменные сборки) есть поле, добавьте `SKIP_DEPENDENCY_INSTALL` = `1`: зависимости и так ставит команда `npm ci`. Можно не добавлять, это только экономит минуту.

   Что делают команды:
   - Build command переходит в корень репозитория (там лежит `package-lock.json` всего проекта), устанавливает зависимости, собирает Mini App (если папка `apps/miniapp` уже есть) и проверяет код. Если фронтенда ещё нет, вместо него показывается страница-заглушка.
   - Deploy command сначала создаёт или обновляет таблицы в базе D1 (уже применённые миграции повторно не выполняются), затем выкладывает Worker.
5. Нажмите **Save and Deploy** (**Deploy**). Первая сборка идёт 2–4 минуты, ход виден в логах на экране.
6. Когда сборка завершится, на странице Worker'а появится адрес `https://honey-loyalty.<ваше-имя>.workers.dev`. Скопируйте его: это **PUBLIC_URL**.

После этого каждый `git push` в `main` будет выкладывать новую версию автоматически.

> Если деплой падает с ошибкой авторизации на шаге `d1 migrations apply` (`Authentication error`, `not authorized`), значит токену сборки не хватает прав на D1. Откройте **Worker → Settings → Build → API token**, нажмите **Edit** или создайте новый токен по шаблону *Edit Cloudflare Workers* и добавьте право **Account → D1 → Edit**. Затем **Deployments → Retry build**.

## Шаг 4. Добавить секреты и переменные

1. Откройте Worker `honey-loyalty` → **Settings → Variables and Secrets**.
2. Нажмите **+ Add** и добавьте по одному. Для секретов выберите тип **Secret**, для переменных **Text**:

   | Тип | Имя | Значение |
   |---|---|---|
   | Secret | `BOT_TOKEN` | токен от @BotFather |
   | Secret | `WEBHOOK_SECRET` | первый случайный пароль |
   | Secret | `SETUP_KEY` | второй случайный пароль |
   | Secret | `TEST_KEY` | третий случайный пароль (только для тестовой версии; в рабочей версии его можно удалить) |
   | Text | `PUBLIC_URL` | адрес из шага 3, например `https://honey-loyalty.amalia.workers.dev` (без `/` в конце) |

3. Нажмите **Deploy** (или **Save and deploy**).

Про `BOT_USERNAME`: можно ничего не делать, шаг 5 сам узнает имя бота у Telegram. Если хотите задать его вручную, впишите имя без `@` в `apps/worker/wrangler.toml` (строка `BOT_USERNAME = ""`). Задавать его в панели бесполезно: значение из файла при следующем деплое перезапишет панель. `PUBLIC_URL` в файле нет, поэтому значение из панели сохраняется (в `wrangler.toml` стоит `keep_vars = true`).

## Шаг 5. Подключить бота: открыть одну ссылку

Откройте в браузере (подставьте свой адрес и `SETUP_KEY`):

```
https://honey-loyalty.<ваше-имя>.workers.dev/setup?key=<SETUP_KEY>
```

Эта ссылка:

- регистрирует вебхук: Telegram начнёт пересылать сообщения бота Worker'у;
- задаёт команды бота `/start`, `/card`, `/lang` (на русском и узбекском);
- ставит кнопку меню «Медовая карта», которая открывает Mini App;
- запоминает адрес приложения и имя бота.

В ответе придёт JSON. Если всё прошло успешно, там будет `"ok": true` и список шагов, у каждого `"ok": true`.

Чтобы сразу назначить себя владельцем (это нужно в рабочем режиме `TEST_MODE = "0"`), добавьте к ссылке свой телефон или Telegram ID:

```
https://honey-loyalty.<ваше-имя>.workers.dev/setup?key=<SETUP_KEY>&owner=%2B998901234567
https://honey-loyalty.<ваше-имя>.workers.dev/setup?key=<SETUP_KEY>&owner=id:123456789
```

`%2B` здесь означает знак `+`. Телефон всегда с кодом страны (`+998…`), Telegram ID — с префиксом `id:` (число из 9 цифр без префикса не принимается: его нельзя отличить от номера телефона). Когда вы поделитесь этим номером с ботом, роль «владелец» привяжется к вашему аккаунту.

После настройки смените `SETUP_KEY` на новый (ссылка с ключом остаётся в истории браузера и в логах).

В @BotFather больше ничего настраивать не нужно.

## Проверка

- [ ] `https://<адрес>/health` отвечает `"ok":true` и `"testMode":true` (`"testUsers"`: `everyone` на полигоне, `listed` при заполненном `TEST_USERS`).
- [ ] `https://<адрес>/` открывает Mini App или страницу-заглушку «Медовая карта».
- [ ] `/setup?key=...` вернул `"ok": true`.
- [ ] В Telegram: `/start` → приходит приветствие на русском со строкой на узбекском, а под полем ввода появляется кнопка «📱 Поделиться номером».
- [ ] Нажмите «📱 Поделиться номером» → придёт «Готово! 🎉 …» с номером карты `HF…`, клавиатура исчезнет.
- [ ] Кнопка «🐝 Открыть медовую карту» или «Медовая карта» в меню открывает приложение.
- [ ] В приложении (тестовый режим) переключитесь на роль «флорист», найдите себя по коду `HF…` или телефону и проведите покупку на 200 000 сум. В бот должно прийти уведомление «🍯 +2 000 мёда…».
- [ ] `/lang` → «🇺🇿 O‘zbekcha» → бот отвечает по-узбекски.

## Если не работает

**Бот молчит после `/start`.**
1. Откройте `https://api.telegram.org/bot<BOT_TOKEN>/getWebhookInfo` (подставьте токен).
   - `url` должен быть `https://<адрес>/telegram/webhook`. Если он пустой, откройте ссылку `/setup` ещё раз.
   - `last_error_message` подскажет причину. `Wrong response from the webhook: 401 Unauthorized` значит, что `WEBHOOK_SECRET` поменяли после настройки: откройте `/setup` ещё раз. `503` значит, что не заданы `BOT_TOKEN` или `WEBHOOK_SECRET`.
2. Проверьте, что секреты добавлены именно в Worker `honey-loyalty` и после этого был **Deploy**.

**`/setup` отвечает `wrong key`.** Значение `key=` не совпадает с секретом `SETUP_KEY`. Проверьте, нет ли лишних пробелов.

**`/setup` отвечает `missing secrets`.** Не добавлены `BOT_TOKEN` или `WEBHOOK_SECRET` (шаг 4).

**Приложение пишет «Нет авторизации».** Mini App нужно открывать из Telegram (кнопкой в боте), а не обычной ссылкой в браузере. Для проверки в браузере в тестовом режиме есть «тестовый вход»: имя плюс ключ `TEST_KEY` (заголовки `X-Test-User` и `X-Test-Key`, их отправляет фронтенд). Без правильного ключа тестовый вход отвечает 401.

**Приложение пишет «Сессия устарела: закройте и откройте приложение заново».** Telegram подписывает данные входа при открытии приложения, сервер принимает их 24 часа. Приложение, открытое дольше, нужно закрыть и открыть снова — это нормально.

**Ошибка `no such table` или `D1_ERROR`.** Миграции не применились. Посмотрите лог деплоя (**Deployments → View build**) на шаге `d1 migrations apply`. Чаще всего причина в неверном `database_id` (шаг 2) или в правах токена (примечание к шагу 3).

**Где смотреть логи.**
- Логи сборки: Worker → **Deployments** → нужная сборка → **View build**.
- Логи работы (запросы, ошибки, `console.log`, ежедневная задача): Worker → **Observability → Logs**. Для живого потока **Logs → Live** (или **Real-time logs**).
- Ежедневная задача: Worker → **Settings → Trigger Events** (Cron Triggers). Там видно расписание `0 * * * *` (каждый час) и время последних запусков.
- Отправленные ботом уведомления: таблица `notifications_log` в D1 (**Storage & Databases → D1 → honey-loyalty → Console**), запрос `SELECT * FROM notifications_log ORDER BY id DESC LIMIT 20;`.

**Нужно начать с чистой базы.** В консоли D1 можно удалить данные, но проще создать новую базу (шаг 1), вписать её ID (шаг 2) и сделать push.

## Тестовый режим (`TEST_MODE = "1"`) и список тестировщиков `TEST_USERS`

Нужен, чтобы показывать приложение и проверять его без настоящих сотрудников. Тестовые возможности:

- переключить себе роль (клиент, флорист, менеджер, владелец) прямо в приложении (кнопка «🧪 Тест»);
- тестовое время: «перемотать на N дней вперёд» и запуск ночной задачи по кнопке — так проверяют сгорание мёда и напоминания;
- демо-данные («Заполнить демо-данными» / «Удалить демо-данные»), сброс своих данных клиента;
- вход из обычного браузера без Telegram: имя и ключ `TEST_KEY` (заголовки `X-Test-User` + `X-Test-Key`). Такие «тестеры» получают выдуманные Telegram ID (от 900 000 000) и никогда не совпадают с настоящими пользователями.

**Кому они доступны — решает переменная `TEST_USERS`** (через запятую: Telegram ID и/или телефоны `+998…`):

| `TEST_MODE` | `TEST_USERS` | Полигон (`dev`) | Заказчик (`main`) |
|---|---|---|---|
| `"0"` | любое | тестовых функций нет ни у кого (рабочий режим) | то же |
| `"1"` | заполнен | только у перечисленных | только у перечисленных |
| `"1"` | пустой | у всех (как раньше) | **ни у кого** (защита: забытый список не открывает экраны владельца посторонним) |

Все, кого нет в списке, видят приложение **ровно как в рабочем режиме**: нет кнопки «🧪 Тест», роль берётся только из таблицы сотрудников (ранее выбранная тестовая роль забывается), `/api/test/*` отвечает 404, вход из браузера не работает. Без этого любой клиент мог нажать «Владелец» и увидеть все телефоны и балансы.

Как указывать людей:

- **Telegram ID** — надёжнее всего. Узнать свой ID: бот @userinfobot. Пример: `TEST_USERS = 123456789, 987654321`.
- **Телефон** `+998…` — засчитывается, когда человек поделился этим номером с ботом («📱 Поделиться номером») или его добавили сотрудником по этому номеру и он вошёл. Пример: `TEST_USERS = +998901234567, 123456789`.
- **Тестер из браузера** — только по ID: добавьте в список число от 900000000 (например `900000001`) и откройте приложение ссылкой `https://<адрес>/?testUser=900000001&testName=Анна&testKey=<TEST_KEY>`. Без такого ID в списке вход из браузера отвечает «этого тестера нет в списке TEST_USERS».

Где задавать: **переменной сборки** (Worker → Settings → Build → Build variables) `TEST_MODE` и `TEST_USERS` — у каждого Worker'а свои. `scripts/select-env.mjs` при сборке впишет их в `wrangler.toml`; лог сборки покажет строку вида `[select-env] … TEST_MODE=1, test features: only TEST_USERS (3)`. В обычных переменных панели (Variables and Secrets) их задавать бесполезно: значение из файла перезаписывает панель при каждом деплое. После смены переменной сборки нажмите **Deployments → Retry build** (или сделайте push).

Тестовое время общее для всех: если тестировщик перемотает его на 30 дней, «сегодня» сдвинется для всех пользователей, ежедневной задачи и бота (у всех, а не только у тестировщиков). Перемотать можно не больше чем на 3650 дней от реального времени. Вернуть время можно кнопкой «сбросить». Когда в боте уже есть настоящие клиенты, часы не трогайте.

Ежедневная задача запускается каждый час и за один запуск обрабатывает до 100 клиентов, у которых сегодня что-то происходит (напоминание или сгорание); остальные — в следующий запуск. Сообщения уходят с 09:00 до 21:00 по Ташкенту, не больше 25 за запуск (переменные `CRON_MAX_CLIENTS`, `CRON_MAX_SENDS`). Кнопка «ночная задача» в тестовой панели делает один такой запуск и отправляет сообщения в любое время суток.

### Переход заказчика в рабочий режим (по шагам)

1. **Владелец и флористы.** Пока тестовый режим включён, проверьте, что владелица (заказчица) нажала в боте `/start` и «📱 Поделиться номером».
2. **Переменные сборки** Worker'а `honeyflowers` (Settings → Build → Build variables): `TEST_MODE` = `0`. `TEST_USERS` можно удалить (при `TEST_MODE=0` он не действует).
3. **Пересборка:** Deployments → Retry build (или `git push` в `main`). В логе сборки — `TEST_MODE=0 (production)`, а `https://<адрес>/health` отвечает `"testMode":false`.
4. **Назначить владельца** (если её ещё нет в «Сотрудниках»): откройте `https://<адрес>/setup?key=<SETUP_KEY>&owner=%2B998XXXXXXXXX` (её телефон; `%2B` — это `+`) или `&owner=id:<её Telegram ID>`. Ответ — `"ok": true` и шаг `addOwner`.
5. **Флористы:** владелица в приложении → «Сотрудники» → добавить по телефону `+998…` или Telegram ID (`id:123456789`) с ролью «флорист». Флорист потом делится номером с ботом — роль привязывается к его аккаунту.
6. **Демо-данные:** если их заполняли, удалите **до** шага 2 (кнопка «Удалить демо-данные» доступна только в тестовом режиме). Тестовые покупки на настоящих клиентах можно исправить корректировкой мёда; если база нужна совсем чистой — создайте новую D1 (шаги 1–2 инструкции для заказчика) до прихода первых клиентов.
7. **Секреты:** смените `SETUP_KEY` на новый, удалите `TEST_KEY` (Settings → Variables and Secrets).
8. **Проверка:** с телефона обычного клиента в приложении нет кнопки «🧪 Тест»; у владелицы — «Статистика», у флориста — касса.

Вернуть тестовый режим: `TEST_MODE` = `1` и `TEST_USERS` = ID тестировщиков, затем Retry build.

### Демо-данные для показа

В тестовой панели («🧪 Тест») есть кнопки **«Заполнить демо-данными»** и **«Удалить демо-данные»**. Первая создаёт около 250 клиентов (узбекские и русские имена, номера +998 настоящих операторов, дни рождения, язык ru/uz) с историей покупок за полгода: постоянные, обычные, разовые, «уснувшие» и ушедшие клиенты, пики к 1 сентября, Дню учителя, 8 марта и т. д., оплата мёдом, открытые и выданные подарки, сгоревший мёд, несколько отмен, 4 демо-флориста. Вся история прогоняется через настоящий движок правил с прошлыми датами, поэтому балансы, соты, уровни и сгорание точно соответствуют правилам.

- Заполнение идёт порциями по 5 клиентов (прогресс «Заполняю… 120/250»), каждая порция укладывается в лимиты бесплатного плана. Повторное нажатие ничего не дублирует.
- Демо-клиенты помечены (`clients.demo = 1`, отрицательные Telegram ID), им **никогда** не отправляются сообщения. «Удалить демо-данные» удаляет ровно их (и все их покупки, мёд, подарки, уведомления) и демо-флористов — настоящие данные не трогаются.
- Заполнение пишет ~19 тысяч строк, удаление примерно столько же (дневной лимит бесплатного D1 — 100 тысяч записанных строк).

## Мониторинг и оповещения

Worker сам пишет в Telegram, если что-то сломалось:

- ошибка сервера (ответ 5xx) в любом маршруте или ошибка в обработчике бота — маршрут, текст ошибки, начало стека, имя окружения;
- ночная задача упала целиком или часть клиентов не обработалась.

Одинаковая ошибка присылается не чаще раза в 15 минут (счётчик повторов хранится в таблице `system_events`), сами оповещения отправляются в фоне и не замедляют и не ломают ответ.

Как включить:

1. Каждый, кто должен получать оповещения, один раз открывает бота и нажимает `/start` (иначе бот не может ему писать).
2. Узнайте его Telegram ID (например, у бота @userinfobot) или ID группы (начинается с `-100…`, бота нужно добавить в группу).
3. Впишите ID через запятую в `ALERT_CHAT_ID` в `apps/worker/wrangler.toml` (секция `[vars]`) **или** добавьте переменную сборки `ALERT_CHAT_ID` у Worker'а (Settings → Build → Variables — так у полигона и у версии заказчика могут быть разные получатели). Значение из файла перезаписывает панель при каждом деплое, поэтому в обычных переменных панели его задавать бесполезно.
4. Необязательно: `ALERT_DAILY = "1"` — раз в день (после запуска в 09:00) приходит короткое «🐝 Ночная задача: ок · проверено 40, напоминаний 3, сгорело у 1 (5 000 мёда), отправлено сообщений 25, в очереди 10».

После каждого запуска ночной задачи (по расписанию или кнопкой в тестовой панели) сохраняется строка в `cron_runs`. Адрес `/health` показывает: доступна ли база (`db`), включены ли оповещения, и итог последнего запуска (`lastCron`: время, статус ok / partial / failed, сколько клиентов проверено, напоминаний, сгорело мёда, ошибок, отправлено сообщений `sent`, ждут в очереди `queued`, подзапросов `subrequests` — должно быть ≤ 45) — удобно для внешнего мониторинга (UptimeRobot и т. п.). `ENV_NAME` (имя окружения в оповещениях) проставляется при сборке автоматически: `<worker> (<ветка>)`.

## Два окружения: заказчик и разработка

| | Разработка (наш полигон) | Заказчик |
|---|---|---|
| Ветка | `dev` | `main` |
| Worker | `honey-loyalty` | `honeyflowers` |
| База D1 | `honey-loyalty` (тестовые данные) | `honey-loyalty-client` (чистая) |
| Бот | `@honeyflowers_test_bot` | бот заказчика |

Оба Worker собираются из одного репозитория. Какой именно получится — решает `apps/worker/scripts/select-env.mjs` по имени ветки, которое Cloudflare передаёт при сборке. Правило: в `main` попадает только проверенное.

### Полигон (уже настроен)

Worker `honey-loyalty` подключён к ветке `dev`. Deploy command у него должен быть:

```
node scripts/select-env.mjs && npx wrangler d1 migrations apply honey-loyalty --remote && npx wrangler deploy
```

### Версия для заказчика (один раз)

1. **Бот.** В @BotFather `/newbot`: имя «Honey Flowers», юзернейм вроде `honeyflowers_bot`. Токен сохранить. Потом бота можно передать заказчику: BotFather → `/mybots` → бот → Transfer Ownership.
2. **База.** Storage & Databases → D1 → Create, имя ровно `honey-loyalty-client`. Скопировать Database ID.
3. **Worker.** Workers & Pages → Create → Import a repository → тот же репозиторий:

   | Поле | Значение |
   |---|---|
   | Project name | `honeyflowers` |
   | Production branch | `main` |
   | Root directory | `apps/worker` |
   | Build command | `cd ../.. && npm ci && npm run build` |
   | Deploy command | `node scripts/select-env.mjs && npx wrangler d1 migrations apply honey-loyalty-client --remote && npx wrangler deploy` |
   | Build variables | `CLIENT_D1_ID` = Database ID из шага 2; `TEST_MODE` = `1`; `TEST_USERS` = Telegram ID / телефоны тестировщиков через запятую |

   Переменная сборки задаётся в Settings → Build → Build variables (это не то же самое, что Variables and Secrets). Без `CLIENT_D1_ID` сборка заказчика намеренно падает. Без `TEST_USERS` тестовые функции у заказчика выключены у всех (даже при `TEST_MODE=1`).
4. **Секреты** Worker `honeyflowers`: `BOT_TOKEN` (бот заказчика), `WEBHOOK_SECRET`, `SETUP_KEY`, `TEST_KEY` — новые случайные строки; `PUBLIC_URL` = `https://honeyflowers.<имя>.workers.dev`. Deploy, затем открыть `/setup?key=…`.

Пока идёт тестирование, у заказчика `TEST_MODE = 1` и тестировщики перечислены в `TEST_USERS` (владелица и её флористы). Перед реальным запуском — «Переход заказчика в рабочий режим» в разделе «Тестовый режим» ниже.

### Как работать дальше

- Разработка в ветке `dev`: `git checkout dev`, правки, `git add -A && git commit -m "…" && git push`. Через 2–3 минуты обновляется полигон и тестовый бот.
- Проверенное переносится заказчику: `git checkout main && git merge dev && git push && git checkout dev`.
- Базы не пересекаются.

## Локальный запуск (для разработчика)

```bash
npm ci
cp apps/worker/.dev.vars.example apps/worker/.dev.vars   # впишите свои значения
npm run dev                                              # = npm run dev -w @honey/worker
# → http://127.0.0.1:8787 (wrangler dev --local, локальная база D1 в apps/worker/.wrangler)
```

```bash
# TEST_KEY из apps/worker/.dev.vars (local-test-key); тестовые id — от 900000000
H='-H X-Test-Key:local-test-key -H content-type:application/json'
```
