# Аудит кода «Медовая карта» — ветка audit/code (HEAD 8ce47d5, база сравнения 86164f2)

Дата: 2026-11-27. Продукт не менялся. Проверочные материалы лежат в этой папке:

- `zz-code-audit.test.ts` — тесты-доказательства для worker (vitest + workerd + D1). Как запустить: скопировать файл в `apps/worker/test/` и выполнить `npx vitest run test/zz-code-audit.test.ts --reporter=verbose` (после запуска файл удалить);
- `worker-proof.log` — вывод этого прогона;
- `css-check.mjs` — скрипт: ищет CSS-переменные без определения и классы из разметки без CSS-правил (`node qa/.out/code-audit/css-check.mjs apps/miniapp`).

## Итог

Базовые проверки зелёные. `npm run typecheck` проходит без ошибок, `npm test` тоже (в worker 227 тестов, в api 13, остальные пакеты зелёные). QA-набор `--only=stock,xss` на портах 8831/8832 проходит без провалов: model run, concurrency, fuzz, roles, mini app e2e, нет 5xx.

Код в целом сильный. Журнал склада неизменяем: движения вставляются одним оператором, кэши ведут триггеры, CHECK `stock_lots_bounds` охраняет остатки, нумерация документов, идемпотентность через `payload_hash`. Деньги считаются в BigInt и milli-сум. Экранирование в Mini App последовательное: я не нашёл ни одной пользовательской строки, которая попадала бы в innerHTML без `esc`.

Перенос стилей на токены прошёл без регрессий по ссылкам: в Mini App нет ни одной неопределённой переменной `var(--…)` и ни одного класса без правила. Из старого `styles.css` не пропал ни один селектор.

Главная найденная ошибка — **CODE-1 (P0)**. Сервер переводит уже **проданный** букет обратно на витрину. После этого букет можно продать второй раз (второе начисление мёда), разобрать или отменить, и стебли возвращаются на склад, хотя продажа остаётся оплаченной. К этому приводит обычная гонка двух телефонов в интерфейсе.

Кроме того, найдены две ошибки P1:

- **CODE-2:** подарки, выданные владельцем, нельзя применить в продаже со склада;
- **CODE-3:** касса флориста «залипает» после потерянного ответа сервера.

Известное ограничение «продажа + мёд в два шага, loyalty_status=failed» я проверил. В целом оно безопасно:

- склад проводится один раз, ключ `sale:<id>` делает второй шаг идемпотентным;
- повтор того же запроса доводит второй шаг до конца;
- гонка двух повторов защищена условием `loyalty_status <> 'done'`;
- продажа без клиента в лояльность не попадает.

Нашёлся один редкий тупик (CODE-6) и одна неточность в сумме мёда (CODE-7).

Счёт находок: **P0 — 1, P1 — 2, P2 — 9, P3 — 10.**

## Что проверено и признано корректным (кратко)

- **Склад, деньги:**
  - сборка по FIFO/FEFO с повтором при гонке (≤ 3 попыток, CHECK `stock_lots_bounds`);
  - сборка «в минус» с комментарием, погашение дефицита приходом;
  - разборка в исходные партии, отходы берутся из старших партий;
  - сторно приходов и списаний, двойные решения дают 409 через триггер `stock_docs_guard`;
  - параллельные продажи одного букета — ровно одна (триггер переходов);
  - округление цены «…5 000», раздельное округление цветов и упаковки;
  - распределение «одной суммой» и дополнительных расходов методом наибольшего остатка (сумма сходится точно);
  - инварианты журнала (`ledgerInvariants`) держатся во всех моих сценариях.
- **Продажа + мёд (два шага):**
  - шаг 1 атомарен (`db.batch`) и идемпотентен (`payload_hash`);
  - шаг 2 идемпотентен по `sale:<id>`;
  - падение между шагами оставляет `pending`: повтор того же запроса или кнопка «Начислить ещё раз» доводят дело до конца;
  - защита от своей карты есть на обоих шагах;
  - отмены складской продажи нет, поэтому двойного возврата мёда быть не может.

  Исключения — CODE-6 и CODE-7.
- **Граница суток Ташкента:** `tashkentDay`/`docDate` (+5 ч, без DST), `dayStartIso`. Расхождений не нашёл.
- **Права:** `/api/stock/*` открыт только сотрудникам, `can()` по таблице, `/api/owner/stock/*` — только владельцу. Веб-сессия кабинета пускается только на `/api/owner/*` и `/api/web/*`. initData проверяется по подписи и сроку (`INIT_DATA_MAX_AGE` по реальному времени). Тестовый вход возможен только с `TEST_KEY`, id ≥ 900 000 000 и по списку `TEST_USERS`.
- **XSS:** все имена, комментарии, причины и ярлыки отмены в новых экранах кассы и витрины проходят через `esc`. Тосты используют `textContent`. QA `xss` зелёный.
- **Производительность:**
  - каталог отвечает 304 по ETag (около 4 строк чтения), использование за 30 дней кэшируется раз в сутки;
  - горячие запросы склада идут по частичным индексам (`stock_lots_pick_idx`, `stock_bouquets_showcase_idx`, `stock_sales_loyalty_idx`);
  - `touchTgUser` пишет не чаще интервала;
  - сканов журнала на горячих путях не нашёл.

## Гипотезы (не подтверждены, в P0/P1 не включены)

- **Тост без вкладок.** У флориста в кассе нет `.tabs`, и тост встаёт на 24 px от низа, то есть может перекрыть кнопку «Собран → продать». Нужен скриншот на телефоне.
