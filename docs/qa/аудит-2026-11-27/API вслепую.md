# Слепой аудит API «Медовая карта» (чёрный ящик, HTTP)

Дата: 27.11.2026. Ветка `audit/blind-api`, локальный Worker + D1 на портах 8821/8822 (инспектор 9821).
Реализацию маршрутов и бизнес-логики не читал. Использовал только `qa/lib/*` (запуск, подпись initData, `/__qa/sql` для чтения базы), регулярку из `qa/suites/fuzz.mjs` (список маршрутов) и названия проверок из существующих наборов, чтобы не повторять уже покрытое.

## Итог

| Приоритет | Кол-во | Коротко |
|---|---|---|
| P0 | 1 | Сборка «в минус» + разборка: склад теряет стебли и их стоимость (API-1) |
| P1 | 3 | Флорист отменяет покупку на своей карте (API-2); флорист забирает себе карту, которую сама открыла по телефону и пополнила (API-3); отмена покупки, созданной продажей букета, не меняет саму продажу (API-4) |
| P2 | 6 | API-5…API-10 |
| P3 | 7 | API-11…API-17 |

Каждая P0/P1 воспроизведена **дважды на новой D1** (`qa/blind/repro.mjs`, лог `qa/.out/blind-api/repro.log`). API-2 и API-3 дополнительно подтверждены **дважды в TEST_MODE=0** с настоящей подписью initData и регистрацией через вебхук бота.

Проверено и работает правильно (подробнее внизу): гонки между разными маршрутами по мёду, подаркам и сотам; сгорание мёда ровно на 180-й день и сброс уровня на 90-й; ДР 29 февраля и окно ДР через Новый год; FIFO с приходом задним числом; отмена поставки параллельно со сборкой; повтор ключа с другим телом для приходов, букетов, продаж, списаний, разборок и подарков; изменение служебных полей через лишние поля в запросе; формулы в CSV через причины, имена сотрудников, заметки и пробел/таб/CR в начале строки; TEST_MODE=0 (демо-маршруты, initData «из будущего», удалённые сотрудник и владелица).

## Как запускать

```bash
cd /home/claude/audit-blind-api
# повторить все P0/P1 дважды на новой базе + TEST_MODE=0 дважды (≈3 мин):
BLIND_OWN_WORKER=1 node qa/blind/repro.mjs
# отдельные проверки — сначала поднять воркер (держать запущенным):
BLIND_OWN_WORKER=1 node qa/blind/serve.mjs &
node qa/blind/deficit-disassembly.mjs   # API-1
node qa/blind/self-ops.mjs              # API-2, API-3
node qa/blind/sale-reversal.mjs         # API-4
node qa/blind/p2-misc.mjs               # API-5…API-9, API-13…API-15
node qa/blind/scale.mjs 1500            # API-10, API-12 (≈3 мин)
# остальные (зелёные): race-stock, race-honey, race-cells, race-reverse-redeem, time, birthday, csv-injection
BLIND_OWN_WORKER=1 node qa/blind/tm0.mjs  # TEST_MODE=0 (свой воркер; serve.mjs перед этим остановить)
```
Каждый скрипт сам очищает базу (`/__qa/wipe`), включает правила владелицы (`useRules('owner')`) и сбрасывает тестовые часы.

## Что проверено и работает правильно (не дублирует `npm run qa`)

- **Гонки между маршрутами** (`race-honey.mjs`, `race-cells.mjs`, `race-reverse-redeem.mjs`, `race-stock.mjs`): продажа букета с мёдом ‖ покупка с мёдом — списано не больше баланса и кешбэка, отрицательных балансов нет. 2 продажи + 2 покупки параллельно — ровно 1 сота и 1 покупочный день. Отмена покупки ‖ выдача её подарка — никогда не проходят обе. Отмена ‖ трата её мёда — корректно. Продажа ‖ разборка, продажа ‖ отмена сборки одного букета — ровно одна операция. Отмена поставки ‖ сборка из её единственной партии — ровно одна. Тот же подарок одновременно в продаже, покупке и выдаче — используется один раз. Инварианты склада и лояльности после всех гонок соблюдаются.
- **Время** (`time.mjs`, `birthday.mjs`): уровень на +89 день сохраняется, на +90 сбрасывается. Мёд на +179 день есть, на +180 сгорает, в том числе у клиента только с приветственным бонусом. ДР 29.02 в невисокосном году: скидка 25.02–03.03. ДР 2 января: скидка открывается 30.12, срок до 05.01. Владелица переносит дату в том же году — второй скидки нет. Границу суток по Ташкенту (00:00 UTC+5) через API проверить нельзя: тестовые часы двигаются только целыми днями, `faketime` в окружении нет. Это ограничение аудита.
- **Деньги/мёд**: чужой подарок в покупке → 404. Подарок со скидкой (сота 10) + мёд → мёд не списывается. То же в продаже букета. Цена букета/услуги ≤ 0, дробная, > 100 млн → 400. Лишние поля (`cashback`, `pct`, `createdAt`, `staffId`, `redeemPoints`, `unitCostMu`, `total`, `paid`) игнорируются. Корректировка/подарок: дробные, > 100 млн / > 10 млн, ≤ 0 → 400. Повтор ключа с другим телом → 409 для приходов, букетов, продаж, списаний, разборок (в том числе на другом букете), `/grant`. Нормализация телефона при начислении по номеру: разные форматы → одна карта; полноширинные цифры → 400. Приветственный бонус при привязке карты начисляется один раз.
- **Склад**: FIFO с учётом прихода задним числом (5 × 10 000 + 2 × 30 000 = 110 000). Задним числом — только владелица и не больше 3 дней, будущая дата → 400. Списать больше остатка → 409. Повтор позиции в списании/букете → 400. «В минус» без комментария (пустой, пробелы) → 400. При политике `block` «в минус» запрещён. Повторное подтверждение/отклонение списания → 409. Отмена «в минус»-сборки возвращает склад точно. Валюта ≠ UZS/USD, курс с > 2 знаками, количество дробное или > 1 млн → 400.
- **Права**: удалённый флорист со свежим initData → 403 на staff и stock. Сессия веб-кабинета удалённой владелицы → 403 (список, CSV, импорт). Флорист не может отменить чужую сборку. Покупка, продажа и выдача подарка на свою карту → 403. Регистрация с номером сотрудника → 403.
- **TEST_MODE=0** (`tm0.mjs`): `/api/test/demo-seed|demo-clear|demo-stock` → 404. initData с `auth_date` на +1 час / +1 год / +50 лет → 401. Без `user` → 401. `user.id` строкой, дробный или > 2^53 → 401. Вебхук без секрета или с неверным → 401.
- **CSV** (`csv-injection.mjs`): формулы `= + - @`, а также таб/пробел/CR в начале — в причинах корректировки, подарка и отмены, в заметках, в имени флориста (Telegram first_name) и в имени сотрудника, заданном владелицей. Ни одна ячейка `clients.csv` / `operations.csv` не начинается с триггера формулы. RFC 4180 соблюдён.
- **Лимиты** (`scale.mjs`, 1500 клиентов): все измеренные HTTP-вызовы ≤ 8 обращений и ≤ 19 выражений к D1. Склад (300 букетов, 40 приходов × 20 строк): overview 2 551 строк, бакеты/свежесть ≤ 4 002. Приход на 60 строк — 18 выражений. Сборка по 40 партиям на позицию — 17. Импорт ограничен 100 строками на порцию.
